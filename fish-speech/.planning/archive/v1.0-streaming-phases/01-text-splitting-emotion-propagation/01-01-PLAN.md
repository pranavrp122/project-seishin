<threat_model>
## Security Considerations

1. **ReDoS (Regex Denial of Service):** The boundary detection regex operates on user-provided text. Patterns like `[.!?]+` and `\[(\w+)\]` are safe -- they use character classes without nested quantifiers or backreferences. The abbreviation lookbehind `(?<![A-Z][a-z])` is fixed-width and cannot cause catastrophic backtracking. Risk: LOW.

2. **Input validation for emotion tags:** The emotion tag regex `\[(\w+)\]` only matches word characters inside brackets. It cannot match arbitrary content like `[<script>]` or `[../../etc/passwd]`. The matched tag name is only used as a string prepended to chunks -- never evaluated, executed, or used in file paths. Risk: LOW.

3. **Memory exhaustion from pathological input:** An extremely long input string (megabytes) could produce many chunks. Mitigation: The existing `chunk_length` parameter (range [100, 1000] per schema.py) and the byte-budget algorithm naturally bound the number of iterations. The function operates in O(n) time and space relative to input length. Risk: LOW.

No additional mitigations needed beyond the existing API-level input validation in `ServeTTSRequest`.
</threat_model>
