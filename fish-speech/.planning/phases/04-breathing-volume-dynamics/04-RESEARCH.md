## Summary

Phase 4 implements two audio-level post-processing features: breathing cues (silence gap insertion) and volume dynamics (gain scaling for asides/emphasis). Both features consume HumanismHints metadata already generated by the Phase 3 TextPreprocessor and apply modifications to audio samples in the streaming inference loop.

The core technical challenges are: (1) mapping text-domain char_offset positions to audio-domain sample positions via proportional mapping, (2) inserting silence gaps without introducing clicks by using cosine ramps at boundaries, (3) applying per-segment gain scaling with smooth transitions, and (4) threading the humanism_hints local variable from line 68 of `__init__.py` through to the three audio processing paths at lines 138, 170, and 188.

All work uses numpy 2.4.4 (already installed). No new dependencies. The architecture follows the established pattern of a lightweight utility class in `fish_speech/utils/` with a dataclass config, similar to `post_fx.py` and `text_preprocessor.py`.

**Primary recommendation:** Build `HumanismAudioProcessor` as a stateless class that takes (audio_array, humanism_hints, text_length, audio_offset_samples, sample_rate) and returns modified audio. Integrate at the three existing `post_fx is not None` guard points.

### Pattern 1: Text-to-Audio Proportional Position Mapping

**What:** Convert char_offset from HumanismHints into sample positions in the generated audio.

**When to use:** Every time a BreathingCue or VolumeHint needs to be applied to audio.

**How it works:** The model generates audio of variable length from text of known length. The relationship is approximately linear -- more text produces proportionally more audio. The mapping formula:

```python
def char_offset_to_sample(char_offset: int, text_length: int,
                          audio_length_samples: int) -> int:
    """Map a text character offset to an approximate audio sample position."""
    if text_length <= 0:
        return 0
    ratio = char_offset / text_length
    return int(ratio * audio_length_samples)
```

**Why approximate is fine (D-14):** Breathing pauses and volume shifts are perceptual effects. A breathing gap placed 100ms earlier or later than the "ideal" position is imperceptible. Human speakers don't breathe at precise positions either. The proportional mapping is sufficient because:
- Breathing cues are at sentence boundaries (long phrases), which correspond to major audio transitions
- Volume changes span entire parenthetical/emphasis regions, not single words
- 44100 samples/sec means even a 5% mapping error on a 3-second utterance is only 150ms -- well within perceptual tolerance

**Critical detail for streaming:** In the streaming loop, audio arrives in segments, not as one complete array. The processor must track cumulative audio offset across segments to correctly map char_offsets. Each call receives the segment plus its offset within the full audio.

### Pattern 2: Stateless Audio Processor with Segment Context

**What:** The `HumanismAudioProcessor` is instantiated once per request but does not maintain IIR filter state like post_fx did. It receives each audio segment with enough context (offset, text length) to apply modifications.

**Why stateless (not stateful like post_fx):** Silence insertion and gain scaling are position-based operations, not state-dependent filters. Each segment can be processed independently given its position in the overall audio.

```python
@dataclass
class AudioProcessorConfig:
    enable_breathing: bool = True
    enable_volume: bool = True
    silence_duration_ms: float = 100.0   # 80-150ms range
    aside_gain: float = 0.85
    emphasis_gain: float = 1.1
    ramp_duration_ms: float = 20.0

class HumanismAudioProcessor:
    def __init__(self, config: AudioProcessorConfig, humanism_hints: HumanismHints,
                 text_length: int, sample_rate: int):
        self._config = config
        self._hints = humanism_hints
        self._text_length = text_length
        self._sample_rate = sample_rate
        self._ramp_samples = int(sample_rate * config.ramp_duration_ms / 1000)
        # Pre-roll breathing cue probabilities at init time
        self._active_breathing_cues = self._roll_breathing_cues()

    def process(self, audio: np.ndarray, audio_offset_samples: int) -> np.ndarray:
        """Process a single audio segment. Returns modified audio (may be longer due to silence insertion)."""
        if self._config.enable_breathing:
            audio = self._apply_breathing(audio, audio_offset_samples)
        if self._config.enable_volume:
            audio = self._apply_volume(audio, audio_offset_samples)
        return audio
```

### Pattern 3: Silence Gap Insertion with Cosine Ramps

**What:** Insert silence of configurable duration at breathing cue positions, with short cosine fade-out/fade-in at boundaries to prevent clicks.

**Verified numpy math:**
```python
# At 44100 Hz:
# 20ms ramp = 882 samples
# 100ms silence = 4410 samples
# Total insertion: 882 (fade-out) + 4410 (silence) + 882 (fade-in) = 6174 samples (~140ms)

ramp_samples = int(sample_rate * ramp_ms / 1000)
t = np.linspace(0, np.pi / 2, ramp_samples, dtype=np.float32)
fade_out = np.cos(t) ** 2  # 1.0 -> 0.0
fade_in = np.sin(t) ** 2   # 0.0 -> 1.0
# Sum is always exactly 1.0 (trig identity: sin^2 + cos^2 = 1)
```

**Implementation approach:**
1. Find the sample position for the breathing cue via proportional mapping
2. Apply fade-out to the audio ending at that position (last `ramp_samples` before the cue)
3. Insert `silence_samples` of zeros
4. Apply fade-in to the audio starting at that position (first `ramp_samples` after the cue)
5. Return the now-longer audio array

**Streaming consideration:** When silence insertion makes the audio segment longer, the offset tracking must account for this. Downstream segments need to know the cumulative insertion offset.

### Pattern 4: Gain Scaling with Cosine Ramp Transitions

**What:** Multiply audio samples by a gain factor (0.85 for asides, 1.1 for emphasis) with smooth transitions at region boundaries.

```python
def _apply_gain_region(self, audio: np.ndarray, start_sample: int,
                       end_sample: int, gain: float) -> np.ndarray:
    """Apply gain to a region with cosine ramp transitions."""
    ramp = self._ramp_samples
    # Ramp in: smoothly transition from 1.0 to gain
    ramp_in_start = max(0, start_sample)
    ramp_in_end = min(len(audio), start_sample + ramp)
    if ramp_in_end > ramp_in_start:
        n = ramp_in_end - ramp_in_start
        t = np.linspace(0, np.pi / 2, n, dtype=np.float32)
        # Interpolate from 1.0 to gain using cosine curve
        ramp_curve = 1.0 + (gain - 1.0) * np.sin(t) ** 2
        audio[ramp_in_start:ramp_in_end] *= ramp_curve

    # Flat region: constant gain
    flat_start = min(len(audio), start_sample + ramp)
    flat_end = max(0, min(len(audio), end_sample - ramp))
    if flat_end > flat_start:
        audio[flat_start:flat_end] *= gain

    # Ramp out: smoothly transition from gain back to 1.0
    ramp_out_start = max(0, end_sample - ramp)
    ramp_out_end = min(len(audio), end_sample)
    if ramp_out_end > ramp_out_start:
        n = ramp_out_end - ramp_out_start
        t = np.linspace(0, np.pi / 2, n, dtype=np.float32)
        ramp_curve = gain + (1.0 - gain) * np.sin(t) ** 2
        audio[ramp_out_start:ramp_out_end] *= ramp_curve

    return audio
```

**Key detail:** Gain of 1.1x on float32 audio can push values beyond [-1.0, 1.0]. Apply `np.clip(audio, -1.0, 1.0)` after all gain operations as a safety limiter.

### Pattern 5: VolumeHint Detection in TextPreprocessor

**What:** Extend the TextPreprocessor to detect aside and emphasis regions from text patterns, producing VolumeHint metadata.

**Detection rules:**
- **Asides (0.85x gain):** Text in parentheses `(...)`, text between em-dashes `-- text --` or `--- text ---`
- **Emphasis (1.1x gain):** Sentences ending with `!`, words in ALL CAPS (3+ chars), text following emotion tags like `[angry]`, `[excited]`

```python
@dataclass
class VolumeHint:
    """Metadata for a volume adjustment region."""
    char_offset: int        # Start of the region
    char_length: int        # Length of the region in characters
    gain: float             # Gain multiplier (e.g., 0.85 for aside, 1.1 for emphasis)
    reason: str             # "aside_parenthetical", "aside_em_dash", "emphasis_exclamation", etc.
```

### Anti-Patterns to Avoid
- **Modifying audio in-place across segments without offset tracking:** The streaming loop yields segments sequentially. If you insert silence in one segment, all subsequent segment positions shift. Track cumulative insertion offset.
- **Applying gain without ramp transitions:** Even a 0.85x gain change produces an audible click if applied as a step function. Always use cosine ramps.
- **Re-enabling post_fx.py:** D-02 explicitly forbids this. The audio processor is a separate, simpler class.
- **Rolling breathing probabilities per-segment:** Roll once at processor init time, not per audio segment. Otherwise a cue at a segment boundary could be rolled differently on retry.

## Common Pitfalls

### Pitfall 1: Silence Insertion Shifts All Subsequent Positions
**What goes wrong:** After inserting a 100ms silence gap at position X, all char_offset-to-sample mappings for positions after X are wrong by 4410 samples.
**Why it happens:** The proportional mapping uses the original audio length, but the audio is now longer.
**How to avoid:** Process breathing cues in reverse order (last position first) OR track a cumulative insertion offset and add it to all subsequent position calculations.
**Warning signs:** Volume changes appear to be applied at wrong positions; second breathing cue lands inside the first silence gap.

### Pitfall 2: Streaming Segment Boundary Splits a Cue Position
**What goes wrong:** A breathing cue maps to sample position 50000, but the current segment only covers samples 45000-48000. The cue is skipped.
**Why it happens:** Audio arrives in variable-length segments in the streaming loop.
**How to avoid:** Two approaches: (a) accumulate all segments before processing (simpler, adds latency), or (b) track which cues have been applied and check each segment against remaining cues.
**Recommendation:** Accumulate all segments in the "final" audio path. For streaming segments, apply only volume changes (which don't change segment length) during streaming, and apply breathing cues to the final concatenated audio. This avoids the segment-length-change problem in streaming.

### Pitfall 3: Gain Clipping on Emphasis Regions
**What goes wrong:** 1.1x gain on a passage that's already near 0.95 amplitude pushes samples to 1.045, causing clipping distortion.
**Why it happens:** Model output amplitude varies; some passages are already near peak.
**How to avoid:** Apply `np.clip(audio, -1.0, 1.0)` after all gain operations. Alternatively, check peak amplitude before applying emphasis gain and reduce the multiplier if needed.
**Warning signs:** Crackling or distortion in emphasized passages.

### Pitfall 4: Breathing Cue Probability Applied Multiple Times
**What goes wrong:** A breathing cue at the boundary between two streaming segments gets its probability rolled twice -- once per segment processing.
**Why it happens:** The processor is called per-segment without tracking which cues have been decided.
**How to avoid:** Roll all breathing cue probabilities once at processor init time. Store the accepted/rejected decision, not the probability. Processing code only checks the decision.

### Pitfall 5: Text Length Mismatch After Preprocessing
**What goes wrong:** Proportional mapping uses the wrong text length because preprocessing changed the text (injected commas, [slow] tags) but HumanismHints char_offsets reference the preprocessed text.
**Why it happens:** `text_preprocessor.py` generates char_offsets in the preprocessed text, but the text is further modified by `split_text_into_chunks()` which strips and re-propagates emotion tags.
**How to avoid:** Use the preprocessed text length (before chunking) as the denominator for proportional mapping. The char_offsets in HumanismHints are relative to the preprocessed text, which is what `req.text` contains after line 69 of `__init__.py`.

## Code Examples

### Example 1: Complete Silence Insertion at a Breathing Cue Position

```python
# Source: Verified numpy operations on numpy 2.4.4
def _insert_silence(self, audio: np.ndarray, insert_position: int) -> np.ndarray:
    """Insert a silence gap with cosine ramps at the given sample position."""
    sr = self._sample_rate
    ramp = self._ramp_samples  # 882 samples at 44100 Hz for 20ms
    silence_samples = int(sr * self._config.silence_duration_ms / 1000)  # 4410 for 100ms

    # Clamp to valid range
    pos = max(ramp, min(len(audio) - ramp, insert_position))

    # Build fade-out (applied to audio before the gap)
    t = np.linspace(0, np.pi / 2, ramp, dtype=np.float32)
    fade_out = np.cos(t) ** 2
    fade_in = np.sin(t) ** 2

    # Split audio at the insertion point
    before = audio[:pos].copy()
    after = audio[pos:].copy()

    # Apply fade-out to the tail of 'before'
    if len(before) >= ramp:
        before[-ramp:] *= fade_out

    # Apply fade-in to the head of 'after'
    if len(after) >= ramp:
        after[:ramp] *= fade_in

    # Build silence gap
    silence = np.zeros(silence_samples, dtype=np.float32)

    # Concatenate: before + silence + after
    return np.concatenate([before, silence, after])
```

### Example 2: Breathing Cue Probability Rolling at Init Time

```python
# Source: Project pattern from text_preprocessor.py breathing cue generation
import random

def _roll_breathing_cues(self) -> list[int]:
    """Roll probabilities for all breathing cues, enforce spacing, return accepted char_offsets."""
    cues = self._hints.breathing_cues
    if not cues:
        return []

    # Count sentences for spacing constraint (BRVL-02: max 1 per 3-5 sentences)
    sentences = [s.strip() for s in re.split(r'(?<=[.!?])\s+', self._hints.original_text) if s.strip()]
    sentence_count = len(sentences)
    max_breathing = max(1, sentence_count // 4)  # ~1 per 4 sentences (middle of 3-5 range)

    accepted = []
    for cue in cues:
        if len(accepted) >= max_breathing:
            break
        if random.random() < cue.probability:
            accepted.append(cue.char_offset)

    return accepted
```

## Detailed Integration Analysis

### HumanismHints Threading (D-13)

The `humanism_hints` variable is currently a local at line 68 of `__init__.py`. The audio processor needs it. Two clean approaches:

**Approach A (recommended): Pass to processor at construction time.**
The audio processor is instantiated once per request (like post_fx was). Pass humanism_hints to its constructor. The processor stores it and uses it throughout the request. This requires no changes to `ServeTTSRequest`, `InferenceResult`, or the streaming loop structure. The processor just replaces the `post_fx` variable.

```python
# Line ~98 of __init__.py (where post_fx was created):
audio_processor = HumanismAudioProcessor(
    config=AudioProcessorConfig(),
    humanism_hints=humanism_hints,
    text_length=len(preprocessed_text),
    sample_rate=sample_rate,
)
```

**Approach B: Store on request object.** Add `humanism_hints` as an attribute on `req` (ServeTTSRequest). This is unnecessary -- the processor already has access via construction.

Approach A is simpler and follows the existing pattern where `post_fx` was a local variable in the inference() method.

### Streaming vs. Final Audio Processing

**Critical design question:** Should breathing silence insertion happen during streaming or on the final audio?

Silence insertion changes the audio array length. In the streaming loop, segments are yielded immediately to the client. If a silence gap is inserted mid-stream, all subsequent audio positions shift -- but the client has already received the earlier audio and cannot un-receive it.

**Recommendation:** Apply volume dynamics (gain scaling) during streaming (it doesn't change array length). Apply breathing silences only to the final concatenated audio. This means:
- During streaming: `process()` applies only gain changes
- After concatenation (the `np.concatenate(segments)` at line 233): `process_final()` applies breathing silences to the complete audio

This avoids the offset tracking complexity during streaming while still delivering both features. The final audio path already concatenates all segments before yielding the `code="final"` result.

**Trade-off:** Breathing gaps won't be audible in real-time streaming -- they appear in the final audio only. For the use case (AI companion), the final audio is the primary output (streaming provides low-latency first audio, but the companion usually plays complete utterances).

### Cumulative Audio Offset Tracking

For volume dynamics during streaming, the processor needs to know where each segment falls in the overall audio. Track this with a simple counter:

```python
cumulative_samples = 0
# ... in the loop:
new_audio = audio_processor.process_volume(new_audio, cumulative_samples)
cumulative_samples += len(new_audio)
```

The `cumulative_samples` value lets the processor compute which VolumeHint regions overlap with the current segment.

## Open Questions

1. **Breathing in streaming segments**
   - What we know: Silence insertion changes array length, complicating streaming offset tracking
   - What's unclear: Whether users care about breathing gaps in real-time streaming vs. final audio
   - Recommendation: Apply breathing only to final audio (simpler, no offset tracking during streaming). Volume dynamics can apply during streaming since they don't change length.

2. **Proportional mapping accuracy**
   - What we know: Text-to-audio ratio is approximately linear but not exact (model has variable generation speed depending on phoneme complexity)
   - What's unclear: How much position error exists in practice
   - Recommendation: Acceptable for perceptual effects. If testing reveals misplacement, add per-sentence mapping (map each sentence's start/end in text to its approximate start/end in audio) for finer granularity.

3. **VolumeHint for emotion tags**
   - What we know: D-09 says emotion tags like [angry] should trigger emphasis gain. The text preprocessor already strips emotion tags during processing.
   - What's unclear: Should we detect emotion tags before or after the preprocessor strips them? The preprocessor's `_insert_slow_tags()` adds [slow] before emotion-tagged sentences.
   - Recommendation: Detect emphasis/aside in the original text (before preprocessing). Store the char_offsets relative to the preprocessed text by remapping after preprocessing. Or simpler: detect in the preprocessed text where [slow] tags (inserted by Phase 3) serve as markers for emotional content.
